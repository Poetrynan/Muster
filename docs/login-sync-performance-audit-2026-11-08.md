# 登录抓取性能审计：减少请求、缩短关键路径（2026-11-08）

状态：完成源码审计与离线复现；没有改动生产登录/抓取逻辑，没有向学校发起测试请求。具体提速幅度需要后续分阶段计时验证。

## 已确认的问题

1. **课程首页与周页面重复下载。** `scraper.rs:2976` 已获取首页用于指纹，但 resources (`:277`)、recordings (`:687`) 和 contacts (`:2256`) 仍分别请求首页；recordings 在拿到首页后又把同一个首页放入抓取队列 (`:708`)。首次同步中，资料和录播还会各自遍历相同的周页面。复用同一次同步中的 HTML，能够在不减少解析结果的前提下减少 HTTP 请求。
2. **录播抓取绕过了增量收益。** 指纹命中仍调用 `fetch_course_recordings`；该函数重新扫描全部发现的 section，没有资料抓取的历史周跳过逻辑。单纯把“课程未变化”当作完整增量优化，实际仍会有大量页面请求。
3. **首屏被全量同步结果牵制。** `Dashboard.tsx:993` 用 Promise.allSettled 等 courses 与 sync 全部完成，之后才写入课程列表。后端 fetch_courses 与 sync_all 都在共享 scraper Mutex 内跨网络 await (`lib.rs:157` / `:269`)；所谓前端并行并不等于两个命令能并行执行。所有课程的详细结果最后整体返回，某个慢页面会拖长可用信息出现时间。
4. **完成进度受任务顺序影响。** 内部课程任务已经并发，但 `scraper.rs:3073` 按 handles 的原始顺序等待，早先的慢课程会延后其他已完成课程的进度通知。应区分“网络任务确实串行”和“完成结果呈现被阻塞”。
5. **限速器在并发下失效。** `throttle.rs:109` 在等待间隔前释放 last_request Mutex，多个等待者会同时醒来并更新时钟；排队获取 semaphore 后还可能再次集中放行。现有顺序间隔/并发上限测试不能覆盖这个组合问题。默认配置为 40ms / 16 并发；注释中的 25 次/秒不是当前实现可以保证的启动上限，也不是学校公布的允许额度。
6. **令牌生命周期需要先修，再降低并发。** 比如 fetch_calendar_events 在同一函数中持有 month 请求的 permit 又获取 upcoming permit；fetch_assignments 的 fallback 也有类似嵌套。直接把并发降到 1–2，可能导致等待自身令牌的死锁。令牌应覆盖一次网络请求/响应体读取，读取结束就释放，不能持有到整个高层抓取函数结束。
7. **失败时可能扩大抓取。** 通用页面读取没有统一处理 HTTP 状态和 Retry-After；课程探测失败又被当作“发生变化”，继续走较重的抓取路径。429/503 时应暂停该主机的背景任务、保留缓存，而不是扩展抓取。
8. **缓存选择缺少明确的缺失/空状态。** targetCourseIds 在首次无课程缓存时不能有效限定当前学期；后端又将没有 cachedWeeks 的课程纳入抓取。includeFixedTabs 由“任何课程已有 UnitInfo”决定，不是逐课程逐页判断。已成功抓取但确实为空的周，也不能仅凭“有没有资源”判断是否同步过。
9. **登录验证和数据刷新混在关键路径。** App 等待 load_saved_session；其中 Moodle 验证、用户资料读取和 Portal 考试检查串在返回前，考试检查可等待至 10 秒。身份与账号绑定验证必须保留，但考试列表等业务数据可以研究在认证完成后刷新，不能直接跳过 Portal 校验来换取速度。

## 离线复现证据

临时探针位于 `.superpowers/login-sync-audit`，直接 import 生产 throttle.rs，没有复制算法，没有发出 HTTP 请求。

参数：20 个同时就绪任务；配置间隔 50ms、并发 16。
观测 grant 时刻（毫秒）：`[0,62,62,62,62,62,62,62,62,62,62,62,62,62,62,62,62,78,78,78]`。
最小相邻间隔：100ns。验证“并发下仍保持启动间隔”的用例按预期失败。
这证明调度器缺陷，不是对学校网络的性能测量，也不构成任何速度提升百分比。

## 建议的实施顺序

### A. 少请求，先保证调度正确

- 添加 auth/Portal/Moodle、锁等待、限速等待、网络、解析、首份可用数据、后台完成的分阶段计时。
- 使用账号/session epoch + URL 的同步周期内 single-flight，复用相同 HTML；同一响应可供资源、录播、公告、联系人等解析器使用。失败不缓存成成功，换账号/登出立即隔离或取消旧任务。
- 将请求 permit 限定在单次请求生命周期；修复真实放行时间的间隔调度与取消行为，再调整并发。
- 统一处理 401/403、429、503 和 Retry-After；重试有上限，等待支持取消。探测失败不能自动触发更大规模抓取。
- 验收：相同 fixture 的可见数据与状态不退化；同一轮相同 URL 最多一个同时在途请求；真实 grant 间隔和并发上限均符合配置；低并发下不会死锁。

### B. 先可用，再补全

- 一次课程发现结果尽快写入 UI，并立即限定当前学期/显式选择的课程。不能无意中给未缓存的历史/隐藏课程开启全量扫描。
- 优先缓存、课程列表、近期截止事项与必要考核状态；历史周、录播、低频资料在后台补全。
- 按完成顺序发出逐课程/阶段结果事件，带 runId、账号 epoch、数据覆盖范围；收到哪些成功结果就合并哪些，失败保留旧数据，成功为空和未获取分开表示。
- scraper 只在取用/切换实例时短暂持锁；克隆后网络执行仍共用同一个 host gate，并通过账号 epoch 防止旧请求回写。不能仅释放锁后再无约束并发。
- 先保留现有认证与账号绑定语义，再分离考试数据读取的等待；不绕过学校的 SSO/MFA。
- 验收：一个录播/历史页超时不会挡住课程和近期事项；切账号、离线、取消、重登不串数据。

### C. 更细的增量与温和刷新

- 缓存按课程/页面记录成功时间、空结果、覆盖范围与指纹，不再只用 cachedWeeks/全局开关推断。
- 成绩与近期提交状态更新得更及时；已评分项目降低频率但保留重评分校验，不能永久当作不变。周次/录播与低频内容使用不同刷新频率；手动刷新可强制校验。
- 只有服务端实际提供并支持 ETag/Last-Modified 时才使用条件请求；304 仍算一次请求，不把主页面指纹当作子页面成绩/公告的完整变更证明。
- 背景刷新加入抖动、失败退避、全局去重；不要每个页面或组件各启动一个轮询器。

## 对学校服务器的约束

优先消除重复和不必要的请求，再用更保守的速率预算。可先试验每客户端后台约 1–2 次请求启动/秒、2–4 个在途请求作为保守起点；这不是学校公布的额度，也不保证在所有用户规模下合适。需要结合实际响应耗时、429/503、失败率与每次同步请求量调整。前台交互应提升队列优先级而不是绕开统一预算。

不进行学校服务器压测，不绕过访问控制，不因追求同步完成时间而无限增加并发。缓存内容需有同步时间与陈旧状态，不能用不刷新换取表面速度。

`requestsUsed` 当前是共享 gate 计数差，不覆盖所有认证、重定向或 WebView 网络行为；后续应按同步 runId 记录逻辑请求、重试、缓存命中、流量及阶段耗时，日志只保留结构化指标，不记录 cookie/token/用户内容。
